# Setup contract

Read for every setup/adoption run. The entrypoint owns mode selection; this reference owns setup scope and completion. User exclusions and existing authorization take precedence.

## Scope

`setup` means create or repair the destination's Markdown instructions and AI-agent skills, then have the relevant agent review their content against the source. Foundation setup does not add project-local helper scripts, JavaScript checkers, Git hooks or CI gates. Existing project-native commands remain owned by the project and run only when its rules or the task require them. Executable automation is outside this workflow. Inspection requests remain `audit`; an explicit document limit remains `documents-only`.

Treat selected skills as required setup deliverables, not optional references. Derive the selected list from the user's requested skills and the workflows the project guide will route to; do not scan unrelated host skills. Before writing, record each selected skill's name, owner/source, intended scope, target path, invocation policy and observed state in `skillInventory`. A skill named in a project workflow is selected and must be installed at that scope or the setup remains partial. The manifest's `requiredSkills` and `skillPaths` must match the complete project-local deliverables, not just the default pair. For each inventory entry, record `name`, `scope` (`project` or `host`), `source`, `path` (project-relative or a non-machine-specific host label), `invocationPolicy`, `installed` and `discoverable`.

For an explicit project-only request, install every selected project workflow skill under a supported project-local path (normally `.agents/skills/<name>`). An existing host installation may supply the source files, but it does not count as a project-local installation. Do not install, configure or modify global skills/settings; preserve their exact pre-setup state. Copy a complete upstream skill folder, including referenced resources, only when its license and host support allow it. If a selected skill cannot be installed or discovered locally, keep the route truthful and report partial setup with the exact gap; never silently omit it or route to a nonexistent capability.

Discover only named upstream skills, executables or services needed by a required/applicable deliverable; do not inventory every host skill, service or installation directory. Verify each selected dependency using the supported catalog and exact relevant install locations. Record installed, discovered, configured, invoked and verified separately. If files exist but discovery omits them, inspect metadata and invocation policy; explicit-only skills are not automatic routes. Repair only the project-local route when supported. Changing global settings or refreshing the host requires its actual supported mechanism. Never claim discovery from disk presence alone or assume an upstream skill exists without evidence.

Preserve skills owned by the host, upstream authors or the project. Before changing a skill location, record the names and paths in that exact target directory and capture selected skill files, settings and callbacks. Install or update only the exact Foundation-owned skill directory through the supported mechanism; never replace or clear a parent skills directory. Do not remove, rename, disable or overwrite another skill. If a selected installed skill such as Impeccable is missing or changes unexpectedly after setup, restore it from the captured pre-setup state or supported host route, verify its discovery, and report any unresolved loss as incomplete setup.

Keep deployment, publication, external tracker writes, global installation/settings and timed background jobs within separately provided scope. Preserve existing automation and disabled states; this workflow does not install or configure hooks.

| Existing skill preservation | Every setup that touches skill files or discovery | Preserve pre-existing host/upstream/project skills and customizations; compare the exact affected skill inventory before and after setup, with no unexpected removal or replacement |
| Selected-skill completeness | Every setup | Inventory each user-requested and workflow-routed skill, install it at the requested scope, list every project-local required skill/path in the manifest, and verify its discovery/invocation state; a missing selected skill keeps setup partial |
| Project skill checklist | Every setup with selected project skills | Create `docs/agents/skills-checklist.md` from the bundled template; list every selected project skill with path, required files, manifest/route status, discovery status and a checkbox; report the total, complete-install count and incomplete count; register the file as `skillChecklist` in the manifest |
| Legacy Foundation cleanup | Existing destination has an older Foundation install | Remove verified Foundation-owned checker/helper scripts (`.mjs` or `.js`), hooks, configuration, active references and project-local planning-skill copies; verify absence while preserving application source files and user/upstream skills |
| Product/current task | Every setup | Reuse current canonical acceptance or create a source-backed task record; distinguish observed behavior, accepted intent and unresolved decisions |
| Architecture/testing | Source exists | Actual entry points and boundaries, Markdown review criteria, and pointers to existing project checks when relevant |
| Domain vocabulary | Confirmed project-specific terms exist | Pure glossary in CONTEXT.md or existing canonical name; implementation, acceptance, decisions and progress retain separate owners |
| Project task skills | Every code-bearing project | Supply both complete skill folders, including testing-contract.md/review-contract.md under their references directories; map bundled sources to the project, route contracts from SKILL.md and register them under the [installation contract](secure-testing-workflows.md#install-or-repair-the-project-skills) |
| Graphify | Code/content discovery is useful | Use an already available upstream tool when useful; installation or refresh automation is outside this Markdown/AI-agent setup |
| Design/Impeccable | UI project where the user selects Impeccable or the project guide routes recurring UI work to it | Write source-backed Markdown guidance; if setup is project-only, install a complete project-local Impeccable skill when supported and leave any host copy untouched; verify local discovery and invocation policy |
| Project planning and tracking | An existing tracker or planning workflow is selected | Reuse the canonical project documents and tracker configuration; do not install unrelated planning skills or create speculative tickets |
| Tool entry points | Project tools are relevant to a selected workflow | Markdown routing to the relevant AI skill, existing native commands and their documented limits |
| Data/security | Persistence, identities or relevant trust boundaries exist | Source-derived ownership/schema/security invariants and AI-agent review criteria; setup does not automatically execute a whole-system scan |
| Requested Mermaid viewer | Explicitly requested, including projects without a schema | Render authoritative schema or supply the pending-schema viewer branch; absence of a DB does not cancel an explicit viewer request |
| Continuation | Every setup | One representative requirement → source → scenario → actual run map and durable next-session pointers |

Adapt artifact names to the destination. Extend a real design guide instead of duplicating DESIGN.md merely for its filename. Avoid inventing product acceptance or an application backlog from code. An unsettled consequential product choice blocks that choice, while independent setup work continues.

Maintain a [document delivery list](document-blueprints.md#document-acceptance)
with required/applicable/excluded/not-applicable classification and reason. Reuse
canonical documents when they already satisfy the contract. Fill missing or
insufficient required content in this run; a file count, empty template, deferred
next command or link back to the whole source does not fulfill that content.

## Perform the setup

1. Build one deliverable list from the request, source, prior open reviews and applicability table. Mark each item required, applicable, excluded or not applicable with a reason, and list its canonical target path. Name every selected skill and its intended install scope before setup; any skill routed as a normal project workflow belongs in this list. Copy [the foundation manifest template](../assets/foundation-profile.template.json) to `docs/agents/foundation.json`; record all required paths, the complete project-local `requiredSkills`/`skillPaths` set, the selected-skill `skillInventory`, and instruction/archive state there. Copy [the skill checklist template](../assets/skills-checklist.template.md) to `docs/agents/skills-checklist.md` and set `skillChecklist` to that path; keep the checklist aligned with the manifest, and report total selected skills plus complete and incomplete counts. Keep it aligned with the delivery list; it is not a reason to delay file creation while unrelated capabilities are inspected.
2. Load only the references and existing upstream instructions needed by that list. Do not install dependencies or tools for standard Markdown/AI-agent setup. If the user explicitly selected an executable capability, follow its supported setup instructions and report unavailable prerequisites accurately.
3. Create or repair every required/applicable document and skill folder from its owner or bundled template, then fill it with confirmed project facts as source work proceeds. Create the foundation report as a working draft with delivery rows and a pending final-review entry. Replace template placeholders with verified content or a clearly owned open item. Archive and rebuild existing instructions using [document blueprints](document-blueprints.md#instruction-migration). For code-bearing projects, follow the [skill installation contract](secure-testing-workflows.md#install-or-repair-the-project-skills), route both default skills from the shared guide, and record their names in `requiredSkills`, paths in `skillPaths` and internal contracts in `documents`. Install additional selected project skills at the requested scope, including complete upstream resources when allowed; do not treat a host-global copy as satisfying a project-only request. When upgrading an older Foundation install, remove legacy Foundation checker artifacts and references and verify their absence using the [AI-agent review migration steps](ai-agent-review.md#upgrade-from-an-older-foundation-install). Preserve every unrelated host/upstream/project skill and verify each selected skill remains installed and discoverable at its declared scope. Adapt upstream routes and invocation policies to verified capabilities. Verification skills inherit mandatory gates rather than redefining them.
4. Create Markdown criteria and route them to the relevant AI-agent skill. Preserve any existing project automation and disabled states unchanged. This setup does not add tools, dependencies, hooks or executable checks.
5. Trace one current journey through its requirement, source and acceptance scenario. Have the appropriate AI skill review the implementation and report file/line evidence. Run existing project-native commands only when repository rules or the current task require them; distinguish those results from the AI review.
6. Have the AI agent review the foundation manifest and delivery list against the destination: open every required/applicable path, inspect all declared project skill folders and their internal contracts/resources, and follow their local links. Compare the selected skill inventory and files with the pre-setup record; verify each declared project skill is locally discoverable and callable according to its invocation policy. Repair unexpected loss only through the supported project-local route or leave setup partial with exact paths and evidence. Confirm no global install/settings changed when project-only was requested. Do not use a bundled JavaScript checker as the project's review mechanism.
7. Finalize the foundation report with per-deliverable status, changes, AI review evidence, any required existing project command results, blockers and continuation. Keep the final-review result structure stable when filling its pending entry. Review semantic consistency separately from file/path presence. Record owned fixture/process cleanup or exact leftovers/blocked cleanup; retain useful evidence outside disposable code with its durable-storage limits.

For explicit-only upstream skills, preserve their invocation/confirmation rules. Reading their templates may support local configuration without claiming that workflow was invoked. Reuse choices already settled by the user; if a prerequisite choice remains consequential, present a concrete draft while completing independent work.

## Completion

- **Complete local setup:** every required/applicable document exists, the AI-agent review covers its content against the source, and local links resolve. Any project-native checks required by existing rules pass. Clearly identify fresh-session or remote outcomes not observed; do not describe them as verified.
- **Partial setup:** required work is still absent or checks have not passed. Name the incomplete deliverables, remedy attempts and next action; continue work while progress is possible.
- **Blocked setup:** a concrete prerequisite prevents the remaining required work. Identify the blocking action/platform limitation and finish independent deliverables first.

Recording `unavailable`, `not configured` or `next action` is evidence reporting, not fulfillment of a required deliverable. An omitted local install because “scope was not separately agreed” is not a valid blocker when setup already authorized it.
